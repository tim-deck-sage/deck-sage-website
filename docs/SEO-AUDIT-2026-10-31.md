## Main finding

The useful public application is fragment-routed (`/#/cards`, `/#/precons`, etc.). The server returns an empty app root, while `/cards/` and `/precons/` return real 404 responses. Google can render JavaScript, but [its guidance explicitly discourages fragments for loading different content and recommends crawlable URLs](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics). The first priority is a small set of useful, directly addressable public pages, not adding keywords to the existing shell or listing hash URLs in a sitemap. A complete app rewrite is unnecessary for a first slice.

## Architecture and privacy constraints

The Next static export already serves actual legal/support pathname pages. The production `preview/tools/assemble.cjs` then copies `preview/public/index.html` over the Next homepage. Consequently, editing only `app/page.tsx` or its Next metadata will not fix the served app homepage. New static pathname pages can coexist with the hash application, provided assembly preserves them and the root public shell is handled deliberately. GitHub Pages does not provide arbitrary application-server rendering; simply switching client routing would leave direct requests broken unless actual exported files exist.

The existing `/privacy-policy/` has a unique title, description and canonical and returns content in its initial HTML: a useful existing pattern. `/core-account-test/` already has `noindex,nofollow`; preserve that callback and all account fixes. Do not add private decks, collection entries, profiles, recovery URLs, account IDs or callback URLs to sitemaps or JSON-LD. Robots directives are not access control; retain current authenticated data gates. Descriptive public pages about private features may be indexed without exposing anyone's data. Do not put a site-wide noindex on the shared root just to hide hash account views.
