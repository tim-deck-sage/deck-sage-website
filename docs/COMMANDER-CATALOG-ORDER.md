# Commander catalog ordering and diagnostics

The Commander Swap UI release reached main in PR #8, but two release attempts stopped at the existing duplicate Oracle identity guard before site build/deployment. Historical failed source bodies were not saved, so the exact offending identities cannot be recovered.

The source request now explicitly specifies `dir=asc` with the existing name order and unique-card query. Two diagnostic captures of the default and explicit ascending requests returned the same 3,692 Oracle identities, printing IDs and normalized card fields. A subsequent live trace reproduced the failure: pages mixed totals of 3,692 and 3,693 with cache ages around 20,000 seconds versus 55 seconds. Keranos, Myrel and War Machine repeated at page boundaries. A no-cache header was ignored by the source cache. Each refresh now appends one random `_ds_refresh` cache token to every trusted search-page URL, including next-page links; this changes no search filters and avoids reusing mixed-age responses. Every page must report the same total, in addition to the original final count and uniqueness guards. No source rows are dropped or deduplicated.

The original exact total / minimum count and Oracle uniqueness conditions remain in force. Duplicate rejection now reports up to ten repeated Oracle identities, with names, printing IDs and page numbers, so another inconsistent response can be traced. The existing trusted pagination host check, freshness/collapse checks, legality normalization, source checksums and atomic publication remain unchanged. No workflow, credential, catalog snapshot or recommendation code changes are included.

Regression coverage exercises explicit query parameters, complete pagination with unchanged records, minimum/exact count rejection, cross-page duplicate rejection and diagnostics, shared refresh-token propagation, mixed-total rejection, and untrusted next-page rejection. The ordinary Linux release workflow still refreshes and validates all sources before deployment.
